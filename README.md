# gamestore-core

Ядро магазина цифровых товаров для геймеров: заказы по SKU, платёжные вебхуки,
автоматическая выдача кодов, два поставщика-заглушки, денежный журнал.

Акцент сделан не на объёме функций, а на надёжности денежного пути: однократная
выдача под гонками, корректная обработка таймаута поставщика, восстановление после
сбоев. Всё это проверяется автоматическими тестами, а не заявляется в тексте.

---

## Быстрый старт

Нужен только Docker. Проверено с чистого клона.

```bash
git clone https://github.com/araratharutyunyan23-max/gamestore-core.git && cd gamestore-core

make up      # зависимости, схема, отдельная БД под тесты, сид (12 SKU и 50 ключей из задания)
make demo    # сквозной сценарий: заказ → вебхук оплаты → выданный код
make qa      # стиль + PHPStan level 9 + все тесты
```

`make demo` на выходе:

```
1. Создаём заказ по SKU KEY-CS2-PRIME
   заказ: ord_00001 — статус created
2. Платёжная система шлёт вебхук paid
   HTTP 200 × 1
3. Ждём асинхронную выдачу

Статус заказа .................. delivered
Состояние оплаты ..................... paid
Выданный код ............. LFXC-TNCS-BPCD
```

Порты нестандартные: приложение `8000`, PostgreSQL `5434`, Redis `6381`,
поставщики `8001` и `8002`.

## API

**Документация: <https://araratharutyunyan23-max.github.io/gamestore-core/>**
— открывается в браузере, ничего запускать не нужно.
[Зеркало без GitHub Pages](https://redocly.github.io/redoc/?url=https://raw.githubusercontent.com/araratharutyunyan23-max/gamestore-core/main/docs/openapi.yaml),
исходник — [docs/openapi.yaml](docs/openapi.yaml).

Тот же контракт доступен и локально после `make up`: **<http://localhost:8000/docs>**.
Там спецификация отдаётся тем же приложением, поэтому не может случиться, что
развёрнута одна версия, а описана другая.

Спецификация сверяется с кодом тестом `OpenApiSpecTest`: каждый публичный
маршрут обязан быть описан, описанных несуществующих маршрутов быть не должно,
а список статусов заказа обязан совпадать с энумом. Расхождение здесь дороже
отсутствия документации — по неверному описанию интегрируются, а правду потом
выясняют отладкой.

| Метод | Путь | Комментарий |
|---|---|---|
| `POST` | `/api/v1/orders` | Заголовок `Idempotency-Key` обязателен; без него 422 |
| `GET` | `/api/v1/orders/{public_id}` | Та же форма ответа, что у создания |
| `POST` | `/api/v1/webhooks/payment` | Всегда 200 на осмысленный JSON; без троттлинга |
| `GET` | `/api/v1/products` | Витрина остатков, курсорная пагинация |
| `GET` | `/ops/reconciliation` | Отчёт сверки, под токеном; 409 при нездоровье |
| `GET` | `/health` | База, кеш и **возраст последней сверки**; 503 при нездоровье |
| `GET` | `/metrics` | Плоский экспорт Prometheus, под тем же токеном |

## Как воспроизвести проверки

### Гонки: 50 параллельных вебхуков

```bash
make race
```

Набор поднимает **свой** экземпляр приложения отдельным процессом и бьёт по нему
настоящим HTTP. Очередь у этого экземпляра синхронная намеренно — тогда каждый из
пятидесяти запросов пытается применить платёж и выдать товар прямо в обработчике,
и конкуренция получается настоящей, а не отложенной.

**Запускать `make race` можно только в одном экземпляре за раз.** Набор занимает
фиксированные порты под свой сервер и заглушки поставщиков и работает по общей
тестовой базе, которую очищает между тестами. Два параллельных прогона дерутся
за то и другое, и падают тесты, не имеющие к правке никакого отношения.

Написано по факту: я сам однажды запустил второй прогон поверх идущего первого
и получил россыпь красного там, где кода никто не трогал. Проверяющему такое
объяснять некому — поэтому оно здесь.

Руками, против поднятого `make up`:

```bash
curl -X POST localhost:8000/api/v1/orders \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: key-1' \
  -d '{"sku":"KEY-CS2-PRIME"}'

# 50 одновременных вебхуков с РАЗНЫМИ event_id
docker compose exec app php artisan shop:webhook ord_00001 --count=50 --parallel

# то же, но честный повтор одного события
docker compose exec app php artisan shop:webhook ord_00001 --count=50 --parallel --same-event-id

curl localhost:8000/api/v1/orders/ord_00001
```

Результат в обоих случаях: 50 событий в инбоксе, **одна** применённая оплата,
**одна** выдача, **одна** проводка признания оплаты, дисбаланс журнала ноль.

### Ловушка таймаута и отказ поставщика

Заглушки управляются предписанно, а не долями вероятностей: тест на вероятности то
воспроизводится, то нет, и красный прогон ничего не доказывает.

```bash
A=localhost:8001; B=localhost:8002

curl -X PUT $A/admin/stock/STEAM-TOPUP-500 -d '{"qty":5}'

# ЛОВУШКА ЗАДАНИЯ: код выдаётся и списывается, но ответ не доходит
curl -X PUT $A/admin/behavior -d '{"mode":"timeout_after_issue","times":1}'

# клиент получает таймаут…
curl --max-time 2 -X POST $A/issue \
  -d '{"request_id":"req_demo-1-A-1","sku":"STEAM-TOPUP-500","order_id":"ord_demo"}'

# …а код уже выдан, и повтор ТЕМ ЖЕ request_id возвращает ТОТ ЖЕ код
curl $A/issue/req_demo-1-A-1
curl -X POST $A/issue -d '{"request_id":"req_demo-1-A-1","sku":"STEAM-TOPUP-500","order_id":"ord_demo"}'

# отказ A и переход на B
curl -X PUT $A/admin/stock/STEAM-TOPUP-500 -d '{"qty":0}'
curl -X PUT $B/admin/stock/STEAM-TOPUP-500 -d '{"qty":5}'
```

Автоматически всё это гоняется в `tests/Race/TimeoutTrapTest.php`.

### Частичный сбой заказа

Заказ из трёх товаров, где выдаётся не всё. Проверяется главное требование
второго этапа: что смогли выдать — остаётся у покупателя, за остальное деньги
возвращаются, и по деньгам сходится.

```bash
# заказ из трёх товаров: один из своего пула, два от поставщика
curl -s -X POST localhost:8000/api/v1/orders \
  -H 'Idempotency-Key: demo-partial' -H 'Content-Type: application/json' \
  -d '{"items":[{"sku":"KEY-CS2-PRIME"},{"sku":"STEAM-TOPUP-500"},{"sku":"SUB-YT-3M"}]}'

# у поставщиков нет товара по двум позициям — выдать их не выйдет
for S in localhost:8001 localhost:8002; do
  curl -s -X PUT $S/admin/stock/STEAM-TOPUP-500 -d '{"qty":0}'
  curl -s -X PUT $S/admin/stock/SUB-YT-3M       -d '{"qty":0}'
done

# оплата (подставьте свой ord_XXXXX)
docker compose exec app php artisan shop:webhook ord_00001

# ЖДЁМ. Позиции от поставщика проходят полный путь — вызов, разбор
# неизвестности, переход ко второму поставщику, — и это занимает до минуты.
# Если посмотреть сразу, увидите промежуточную картину: часть позиций ещё
# в delivering, а заказ в paid. Это не поломка, это работа в процессе.
until curl -s localhost:8000/api/v1/orders/ord_00001 \
      | jq -e '.data.items | all(.status != "delivering" and .status != "pending")' >/dev/null
do sleep 5; done

# состояние: одна позиция delivered, две — в тупике
curl -s localhost:8000/api/v1/orders/ord_00001 | jq '.data.items'

# терпение перед возвратом настраивается; в демо его можно обнулить
docker compose exec -e DELIVERY_REFUND_AFTER_MINUTES=0 app \
  php artisan orders:settle-abandoned

curl -s localhost:8000/api/v1/orders/ord_00001 | jq '.data | {status, items}'
```

Запускать расчёт раньше, чем позиции дойдут до тупика, бессмысленно: он
ответит «позиций к возврату нет» — и будет прав. Позиция в `delivering` не
возвращается никогда, сколько бы ни висела: там судьба обращения к поставщику
может быть НЕИЗВЕСТНА, и вернуть деньги за товар, который поставщик всё-таки
выдал, значит отдать и товар, и деньги.

Реальный вывод последней команды:

```
статус заказа: partially_delivered
  1 KEY-CS2-PRIME   -> delivered | код: есть
  2 STEAM-TOPUP-500 -> refunded  | код: нет
  3 SUB-YT-3M       -> refunded  | код: нет
```

`partially_delivered` — **конечное** состояние: заказ рассчитан, и возвращаться
к нему незачем. Этим оно отличается от `delivery_failed`, из которого дорога
назад в выдачу есть. Автоматически — `tests/Feature/Ordering/PartialSettlementTest.php`.

### Недобросовестный поставщик

```bash
A=localhost:8001; B=localhost:8002
curl -s -X PUT $A/admin/stock/STEAM-TOPUP-500 -d '{"qty":5}'

# 1. один код двум покупателям
curl -s -X PUT $A/admin/behavior -d '{"mode":"duplicate_code","times":1}'

# 2. код от другого товара
curl -s -X PUT $A/admin/behavior -d '{"mode":"foreign_code","times":1}'

# 3. ошибка ПОСЛЕ настоящей выдачи
curl -s -X PUT $A/admin/behavior -d '{"mode":"error_after_issue","times":1}'
```

Во всех трёх случаях код покупателю не уходит, а расхождение попадает в сверку:

```bash
curl -s -H "X-Ops-Token: $OPS_TOKEN" localhost:8000/ops/reconciliation | jq '.anomalies'
```

Автоматически — `tests/Race/DishonestSupplierTest.php`.

### Как проверить, что деньги сходятся

Три способа, от самого короткого к самому подробному.

```bash
# 1. Одним числом: расхождение журнала обязано быть нулём
curl -s -H "X-Ops-Token: $OPS_TOKEN" localhost:8000/metrics | grep imbalance

# 2. Сверка: она молчит на здоровых данных и отвечает 409 на нездоровых
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "X-Ops-Token: $OPS_TOKEN" localhost:8000/ops/reconciliation

# 3. Остатки счетов на любой момент и обороты за период
curl -s -H "X-Ops-Token: $OPS_TOKEN" 'localhost:8000/ops/ledger' | jq '.data.balances'
```

Вывод третьей команды на состоянии из примера выше:

```json
{
  "customer_prepayment": 0,
  "gateway_receivable": -457000,
  "refunds_payable": 199000,
  "revenue": 258000
}
```

Читается напрямую: получено 457 000 копеек, из них 258 000 признано выручкой за
выданный товар и 199 000 висит долгом перед покупателем за невыданный.
**258 000 + 199 000 = 457 000**, а обязательство отдать товар закрыто в ноль.
Это и есть «оплачено = выдано + возвращено», увиденное глазами.

Ключевой инвариант второго этапа записан так, что его проверяет база: у заказа,
дошедшего до конечного состояния, остаток по `customer_prepayment` равен нулю. Обнулить его может только выдача (в выручку)
или возврат (в долг перед покупателем), третьего способа нет. Держит отложенный
`CONSTRAINT TRIGGER`; попытка закрыть заказ с незакрытыми деньгами не проходит
коммит — см. `tests/Race/SettlementGuardTest.php`.

### Состояние на любой прошедший момент

```bash
curl -s "localhost:8000/api/v1/orders/ord_00001?as_of=2026-09-08T10%3A00%3A00%2B00%3A00" | jq
curl -s -H "X-Ops-Token: $OPS_TOKEN" \
  'localhost:8000/ops/ledger?from=2026-09-08T00%3A00%3A00%2B00%3A00&to=2026-09-08T23%3A59%3A59%2B00%3A00' | jq '.data'
```

`+` в смещении часового пояса обязательно кодировать (`%2B`): в query-строке он
означает пробел, и без кодирования запрос вернёт `422`. Отказ здесь лучше
догадки — подставлять «наверное, UTC» в вопрос о деньгах нельзя.

Момент раньше создания заказа отвечает честно, а не ошибкой:

```json
{ "id": "ord_00516", "as_of": "...", "existed": false }
```

А обороты за период сходятся с остатками по каждому счёту — `opening + turnover
= closing`:

```
opening   gateway_receivable -129000   revenue 129000
turnover  gateway_receivable -328000   revenue 129000   refunds_payable 199000
closing   gateway_receivable -457000   revenue 258000   refunds_payable 199000
```

## Критерии приёмки

Каждый закрыт тестом. «Ровно один раз» в этом проекте всегда обеспечено
ограничением БД, а не аккуратностью кода, поэтому у каждой гарантии есть имя индекса.

| № | Критерий | Тест | Чем обеспечено |
|---|---|---|---|
| 1 | 50 параллельных вебхуков → одна выдача | `ParallelWebhookTest` (два варианта: один `event_id` и 50 разных) | `payment_events_one_applied_paid_uq`, `deliveries_order_item_uq` |
| 2 | Повтор с тем же `event_id` ничего не меняет | `PaymentWebhookTest` | `payment_events_event_id_uq` |
| 3 | Вебхук вне порядка или раньше заказа | `ParallelWebhookTest`, `ApplyPaymentEventTest` | монотонный upsert проекции + инбокс |
| 4 | Таймаут поставщика, который выдал код | `TimeoutTrapTest` | `delivery_attempts_item_open_uq`, детерминированный `request_id` |
| 5 | A недоступен → fallback на B → один раз | `TimeoutTrapTest` (3 сценария) | `delivery_attempts_item_success_uq` |
| 6 | Пустой остаток → восстановимо, без падения | `PoolDeliveryTest` | `GREATEST(count - 1, 0)` вместо `CHECK` как ворот |
| — | Журнал не сходится → коммит отбит | `DeferredLedgerTriggerTest` | `CONSTRAINT TRIGGER ... INITIALLY DEFERRED` |

### Витрина под объёмом

```bash
make bulk       # сгенерировать 5000 SKU
make explain    # план выполнения горячего запроса
```

Замер на 5012 товарах:

```
Узел плана ............. Index Only Scan
Индекс ................. products_showcase_cov_idx
Обращений к куче ....... 0
Страниц прочитано ...... 4
Время выполнения, мс ... 0.083
```

**Как это читать.** `Index Only Scan` означает, что база не открывала основную
таблицу вообще: все нужные колонки лежат в самом индексе. `Heap Fetches: 0` —
прямое доказательство этого, а не косвенный признак. Четыре страницы вместо
сотен — стоимость страницы не зависит от размера каталога, потому что читается
ровно тот кусок индекса, который нужен.

**Что было до правки.** Первая версия индекса включала `(sku, name, currency)`,
а запрос выбирает ещё и `supply_mode` — по нему решается, показывать ли остаток
вообще. Одной недостающей колонки хватило, чтобы план стал обычным `Index Scan`:
**27 страниц вместо 4**. «Покрывающий индекс» — это не свойство индекса, а
отношение между индексом и конкретным запросом, и проверяется оно только планом.

Это же проверяет тест `ShowcasePlanTest`: он утверждает `Index Only Scan` и
`Heap Fetches: 0` на трёх тысячах товаров. Утверждение о производительности без
`EXPLAIN` под ним — не утверждение.

### Сверка

```bash
docker compose exec app php artisan shop:reconcile --full

# то же по HTTP; 409 при нездоровье, чтобы вешать прямо в мониторинг
curl -H "X-Ops-Token: $OPS_TOKEN" localhost:8000/ops/reconciliation
```

Восемь детекторов, включая оба вопроса задания: **«оплачен, но не выдан»** и
**«выдан, но не оплачен»**. Возраст открытой позиции считается после агрегации,
а не фильтром по строкам — иначе каждый заказ, выданный позже порога, помечался бы
критической аномалией, и сверка была бы красной на счастливом пути.

Ожидание пополнения склада — **warning, а не critical**: заказ в `out_of_stock` это
пауза, и если считать её инцидентом, система будет красной ровно тогда, когда
работает штатно.

Отдельно проверено, что сверка **молчит на здоровых данных**. Сверка, которая шумит
на штатной работе, бесполезна: её перестают читать через неделю.

## Ключевые решения

### Гарантии живут в БД, а не в коде

Правило проекта: **любая фраза «ровно один раз» обязана назвать индекс, который это
обеспечивает.** Утверждение без индекса — не гарантия, а надежда. Тест
`SchemaContractTest` проверяет 12 таких соответствий и заодно сверяет каждый
PHP-энум с `CHECK`-ограничением в схеме.

19 таблиц, 40 уникальных индексов, 7 триггеров. Несбалансированная проводка
отвергается отложенным `CONSTRAINT TRIGGER` на COMMIT, журнал неизменяем, из
финального статуса заказа выхода нет ни из кода, ни из psql, ни из миграции.

### Приём вебхука не делает ничего, кроме приёма

Одна короткая вставка в инбокс и `200 OK`. Синхронная выдача связала бы SLA
платёжной системы с доступностью поставщика: таймаут превращался бы в 5xx,
платёжка повторяла событие — и мы сами порождали бы ту волну параллельных
вебхуков, которую потом обязаны пережить.

Диспатч задачи принимается **по состоянию**, а не по факту вставки:

```php
$this->events->insertIgnoringDuplicates($data);      // ON CONFLICT DO NOTHING
if ($this->events->isUnapplied($data->eventId)) {    // ← читаем состояние
    ApplyPaymentEventJob::dispatch($data->eventId)->afterCommit();
}
```

`if ($inserted) dispatch(...)` теряет платёж навсегда: падение между COMMIT и
постановкой задачи означает, что все повторы уйдут в `DO NOTHING`, и задача не
встанет уже никогда.

### Идемпотентность оплаты — по заказу, а не по событию

Контракт обещает тот же `event_id` на повтор, но критерий приёмки допускает
**50 разных** `event_id` по одному заказу. При ключе по событию журнал получил бы
50 проводок и остался бы при этом идеально сбалансированным — то есть сломался бы
незаметно. Ключ строится как `payment_captured:{order_id}`.

### Состояние оплаты отделено от состояния заказа

Поздний `failed` обязан стать правдой о деньгах, но не имеет права отменить уже
отданный клиенту код. Поэтому платёж живёт в отдельной проекции с монотонным
upsert по кортежу `(occurred_at, received_at, id)`, а выдача **читает проекцию, а
не статус заказа**: в окне между признанием оплаты и стартом выдачи статус уже
`paid`, и проверка по статусу такой отзыв не поймает.

### Таймаут ≠ отказ

Центральное решение всего задания.

Исход вызова классифицируется по паре (фаза транспорта, разобранный конверт), а не
по HTTP-коду: `500` мог прилететь от прокси уже после того, как код закоммичен.
Доказанным отсутствием выдачи считаются только конверт `4xx` с бизнес-причиной и
несостоявшееся соединение.

`request_id = req_{заказ}-{поставщик}-{эпоха}` и **не зависит** от номера сетевой
попытки — поэтому повтор после таймаута возвращает тот же код, а не покупает второй.

И главное: **`probe → 404` не даёт права уйти ко второму поставщику.** Probe может
обогнать ещё живую обработку и ответить «не знаю такого» за миллисекунды до выдачи
кода. Поэтому заглушка помечает запрос принятым **до** любых задержек
(claim-before-work) и умеет `POST /issue/{id}/seal` — обязательство никогда не
выдавать код по этому `request_id`. Замок снимает только печать или доказанный отказ.

### Порядок шагов выдачи

Не стиль, а требование корректности — нарушение любого стоит второго кода:

1. Строка попытки **коммитится до** сетевого вызова: падение процесса ровно в момент
   таймаута оставляет след, по которому повторяется тот же `request_id`.
2. Вызов идёт **вне транзакции**: иначе блокировки держатся все секунды таймаута,
   а при сбое пришлось бы выбирать между откатом (стирает единственное
   доказательство, что запрос ушёл) и удержанием транзакции.
3. Полученный код пишется **отдельной микротранзакцией** до привязки к заказу:
   исключение в бизнес-логике иначе откатывает уже купленный код.
4. Переход к B — только после доказанного отсутствия выдачи у A.

### Взаимное исключение — аренда, а не статус

По статусу нельзя отличить «я начал выдачу» от «выдачу ведёт другой воркер»:
переход `delivering → delivering` запрещён в обоих случаях. Аренда с
fencing-токеном отвечает однозначно — условный `UPDATE` затронул одну строку.
Протухшая аренда перехватывается по времени, поэтому упавший воркер не блокирует
заказ навсегда.

### Деньги

Только целые копейки (`bigint`), двойная запись, журнал только на добавление.
`SUM(amount_signed) = 0` **ничего не доказывает** — две ошибочные проводки тоже дают
ноль, поэтому сверяются остатки по счетам.

## Что осталось за рамками

Честно, чтобы не создавать ложного впечатления.

- Оба этапа закрыты целиком, включая обе бонусные задачи второго. Из
  необязательного не сделано: ручной ретрай выдачи из админки, партиционирование
  журнала, алертменеджер с правилами — всё это описано в разделе о
  масштабировании как «куда расти».
- Заказ — список позиций, у каждой `quantity = 1`. Количество как отдельное поле
  не введено намеренно: две штуки одного товара — это две позиции и два кода,
  и такая модель не теряет ни одного требования, зато убирает целый класс
  ошибок в журнале (проводка суммы заказа вместо суммы позиции).
- **Возврат денег не отправляется в платёжную систему.** Он проводится по
  журналу и висит долгом на счёте `refunds_payable`. Реальной выплаты нет
  по той же причине, по которой нет реальной оплаты: платёжная система —
  заглушка. Долг при этом виден, а не списан «в никуда».
- **«Код от другого товара» ловится по SKU, объявленному поставщиком.** Полной
  защиты тут быть не может: что открывает чужая строка символов, снаружи не
  узнать. Дубль кода, в отличие от этого, ловится независимо — мы помним каждый
  код, который когда-либо получали.
- `amount` в вебхуке трактуется как **мажорные единицы** (рубли), как в примере
  задания. Допущение изолировано в `MoneyParser` и покрыто тестом.
- Подпись вебхука не проверяется — по условию задания.

## Как масштабировал бы под нагрузку

**Витрина** уже сделана так, как надо: keyset-пагинация вместо `OFFSET`, покрывающий
индекс с `INCLUDE` ради `Index Only Scan`, остатки вторым запросом вместо `JOIN`
к самой перезаписываемой таблице. Дальше — кэш страницы в Redis с коротким TTL.
Устаревший остаток на витрине допустим, при резерве — нет.

**Счётчик остатка популярного SKU** — точка сериализации: при десятках параллельных
покупок одного товара воркеры выстраиваются на `UPDATE` одной строки. Лечится
шардированием счётчика (N строк на SKU с суммированием) либо переносом декремента
в асинхронный аккумулятор. Источник истины при этом остаётся в `license_keys`.

**Флаг `in_stock`** стоит в предикате индекса, поэтому каждое его переключение —
non-HOT update. На SKU с глубоким пулом это незаметно, на дефицитных позициях
частота флипа равна частоте продажи. Смягчение — снимать флаг фоновым дебаунсом,
а не в транзакции продажи.

**Журнал и инбокс** растут монотонно и не чистятся — это аудит. На реальном трафике
потребуется партиционирование по времени; worklist-индексы от этого не пострадают,
потому что они частичные и покрывают только незавершённые строки.

**Сверка** должна стоить `O(аномалий)`, а не `O(истории)`: для этого проекция
открытых позиций журнала, поддерживаемая триггером, вместо `SUM` по всей книге.

## Затраченное время

**Первый этап** — около 18 часов: 31 коммит, 8 pull request.

**Второй этап** — около 14 часов: 9 коммитов, по одному на шаг плюс две сверки.
Из них заметная часть ушла не на новый код, а на проверку собственных
утверждений — и снова окупилась.

Заметная часть ушла не на написание функций, а на проверку собственных
утверждений — и это оказалось самым полезным вложением. Самые дорогие находки
все одного рода: тесты, которые были зелёными и при этом проверяли не то, что
заявляли.

Три этапа подряд тесты шли по боевой базе с очередью `redis`, из-за чего **ни
одна фоновая задача не исполнялась в тестах ни разу**. `make up` на чистом клоне
не работал вовсе — зависимости никто не ставил. Быстрой сверки не было в
расписании, и пять детекторов денежных расхождений запускались раз в сутки
вместо раза в минуту. Отложенность триггера баланса не проверялась на настоящем
коммите, то есть проверялась функция, а не свойство, ради которого триггер
объявлен `DEFERRED`. Разбор суммы отвергал `{"amount": 1290.00}` и терял
оплаченный заказ молча.

Ни одно из этого не находилось чтением кода. Всё нашлось запуском: клон в пустой
каталог и дальше строго по README, `/health` на свежем окружении, снятие
триггера ради проверки самого теста. Поэтому в проекте так много сторожевых
тестов — правило, которое держит только память, правилом не является.

На втором этапе повторилось то же самое, и находки были того же рода.

Гейт шага о выдаче по позициям я объявил выполненным раньше времени: план
обещал заказ, где «один поставщик отдаёт код, второй молчит, третий отказывает»,
а состязательные тесты я написал только на товары из собственного пула — пул
по сети не ходит, и независимость позиций на нём не доказать. Реализация
оказалась верной, не хватало проверки.

Первая версия триггера «сумма позиций равна итогу заказа» была написана
с ошибкой, и **весь обычный набор остался зелёным**: под `RefreshDatabase`
транзакция не коммитится, а отложенный триггер срабатывает только на коммите.
Поймал состязательный набор.

Фикстура «загнать позицию в тупик» переводила её в `delivery_failed` — и тест
упал, потому что система штатно повторила выдачу и выдала товар. Это оказалось
правдой о системе, а не о тесте.

И дважды тест был зелёным по посторонней причине: один раз падал не тот
триггер, другой раз проверка по подстроке принимала чужую ошибку. Оба чинились
одинаково — сверкой точного текста.
